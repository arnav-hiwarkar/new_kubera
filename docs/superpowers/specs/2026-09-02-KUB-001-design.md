# KUB-001: Server-side Module Gate Enforcement

## Overview
This document covers the architectural and tactical fixes applied for KUB-001: Module access control enforced only in the browser for 7 of 10 modules. The backend was previously relying on frontend `<Navigate>` protection rather than API-level barriers for many modules.

## 1. Context & Vulnerability
Any user authenticated to the company via `/api/v1/auth/company/login` with `accessible_modules: []` could directly call API routes corresponding to modules like DocVault, AuditEase, Activity Log, etc., bypassing intended constraints.

## 2. Proposed Architecture & Pattern
- **Centralized Constants:** Add explicit declarative identifiers for all available modules in `app/access_modules.py`.
- **API Router Hardening:** Add `dependencies=[Depends(require_module("<module_id>"))]` to every missing `APIRouter`.
- **Robust Model Validation:** Apply input validation directly into Pydantic models (`UserCreate` and `UserUpdate`) rejecting the assignment of non-existent module IDs using a newly defined `validate_accessible_modules`.
- **Testing Approach:** Rely on Python AST / dependency inspection (`test_every_module_router_has_a_server_side_gate`) to definitively prove that no endpoints are skipping the `require_module` check. Supplement with E2E endpoint checks fetching 403 HTTP codes on missing access.

## 3. Trade-offs
- Adding `Depends(require_module())` at the router level forces strict enforcement across *all* sub-routes. This is desired for security, but limits exposing any public non-auth endpoint from these specific module files (which is intentionally not a use case here).
- Validating inputs limits backward compatibility for unknown strings, forcing migration/coordination if new frontend IDs ever float in before the backend learns of them. This is functionally a strong security gain.

## 4. Verification Status
Verified against a live PostgreSQL test database (2026-09-02):

- `tests/test_module_enforcement.py` — 10 tests. Covers the structural sweep (66
  routes across the six routers, each carrying exactly its own module gate), the
  negative case (empty `accessible_modules` -> 403 on all six), the **positive**
  case (granting one module opens exactly that module and still blocks the other
  five), admin bypass, unauthenticated rejection, write-side validation of unknown
  module ids on create *and* update, and a frontend/backend drift guard that
  compares `ALL_MODULES` to `MODULE_DEFINITIONS` in `modules.ts`.
- Regression sweep of every test file that touches a gated endpoint or creates
  users: docvault (incl. approvals and bucket RBAC), auditease (incl. RBAC,
  reports, multi-auditor, requirement submissions), sales, kra, assets, compliance,
  activity/notifications, user access, user RBAC, auth, onboarding, custom fields.
  ~290 tests, all passing.
- Live probe of the running container confirms the deployed image carries the
  gates and that the six routers reject unauthenticated (403) and bad-token (401)
  requests.

### Regressions found and fixed during verification
`tests/test_docvault_approvals.py` provisioned members with `["docvault"]` only,
then read `/api/v1/notifications` to assert approval notifications were delivered.
Under the new gate that returns 403. This was a genuine product signal, not just
test drift — see the "Operational Consequence" note in
`docs/security_checks_notes.md`. Test members now receive
`["docvault", "notifications"]`.
