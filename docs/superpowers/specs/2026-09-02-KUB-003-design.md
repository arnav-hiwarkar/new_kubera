# KUB-003: Insufficient Anti-Automation

## 1. Context & Vulnerability
Multiple authentication endpoints, including `/auth/auditor/login`, `/auth/auditor/register`, and the token refresh endpoints, lacked rate limiting. The `enforce_rate_limit` utility completely failed open if Redis was unavailable, meaning throttling would silently vanish. Because the rate limiter only keyed on `(IP, Email)`, brute-forcing many different emails from the same IP (credential stuffing or enumeration) bypassed the throttling entirely. Furthermore, there were no edge-level Nginx rate limits to stop large-scale volumetric attacks.

## 2. Proposed Architecture & Pattern
- **API Rate Limiting Hardening:**
  - Add `ip_limit` and `ip_window` support to `enforce_rate_limit` in `app/rate_limit.py` to allow limiting brute-force attempts per IP independent of the identifier.
  - Fail-open in `enforce_rate_limit` will now log an error so it is visible in the application logs.
  - Apply `enforce_rate_limit` to `company_login`, `company_refresh`, `auditor_register`, `auditor_login`, and `auditor_refresh` with strict IP-based limits (e.g., 50 requests / 5 mins for login).
- **Edge Nginx Hardening:**
  - Introduce new shared memory zones (`limit_req_zone`, `limit_conn_zone`) in a new `/etc/nginx/conf.d/limits.conf`.
  - Update `gateway/modes/app.conf` to explicitly protect `/api/v1/auth/` (`limit_req zone=api_auth`) and globally limit `/api/` (`limit_req zone=api_general`, `limit_conn`).

## 3. Trade-offs
- **Redis fail-open** provides high availability for logins if the store goes down, but
  temporarily sacrifices brute-force protection. It logs at ERROR with a traceback, so
  outages alert rather than going unnoticed, and the Nginx zones keep working meanwhile.
- **Every "per-IP" limit here is really per-customer.** Kubera is B2B; an entire office
  shares one NAT address. `limit_req ... nodelay` rejects past burst rather than queueing,
  and a 429 on `/auth/*/refresh` is a forced sign-out, so a limit tuned for one user turns
  a tenant's Monday morning into an outage. `api_general` is therefore a loose ceiling
  (50r/s, burst 100) and the security work is done by `api_auth` (1r/s over the four
  credential URIs) and `limit_conn` (200, the control that actually bounds the api
  container's memory, since uploads and report renders cost concurrency not request rate).

## 4. Review corrections
The first implementation shipped with three defects, found on review and fixed before
this was considered done:

1. **The Nginx zones were keyed on a constant.** `$binary_remote_addr` with no `real_ip`
   configuration is Caddy's address on the `edge` network — identical for every visitor —
   so the entire user base shared one 1r/s bucket and ten requests from one client locked
   everyone out. Confirmed against the running stack (`limiting requests ... client:
   172.19.0.3`, Caddy) and fixed with `set_real_ip_from`/`real_ip_header`/
   `real_ip_recursive off` in `gateway/limits.conf`; the same log line now reads
   `client: 172.19.0.1`.
2. **A `location ^~ /api/v1/auth/` prefix swept normal traffic into the 1r/s bucket** —
   `/auth/company/me` and `/auth/*/refresh` (called on every app boot and route guard)
   and `/auth/companies` (driven in bulk by `ops/kubera-import.sh`) — and duplicated the
   proxy stanza while dropping `proxy_read_timeout` and `proxy_request_buffering`. The
   strict zone is now selected by a `map` over the exact credential URIs, from the single
   existing `location /api/`.
3. **The Retry-After lookup sat outside the fail-open `try`**, so a Redis that survived
   `INCR` but not `TTL` raised a 500 out of the login endpoint. All store access is now
   inside the block, and `TTL`'s -1/-2 sentinels fall back to the window instead of
   emitting `Retry-After: -2`.

Also corrected: the two counters were `rl:{scope}:{ip}:{identifier}` and
`rl:{scope}:ip:{ip}`, which collide when `ip` is the literal string `ip`; the limits were
hardcoded in the router rather than in `app/config.py`; and the accompanying test file
asserted `401` for the first 50 login attempts when the per-identifier limit is 10, so it
had never passed.

## 5. Final Status
Backend endpoints are throttled on both axes, the Nginx zones key on the real client, and
429s carry a `Retry-After` the SPA renders. Covered by `tests/test_rate_limits.py` (17
tests, including anti-tests for cross-client bleed, key poisoning, fail-open and the kill
switch), `unit_tests/test_deployment_hardening.py::TestEdgeRateLimits`, and
`frontend/src/api/rateLimit.test.ts`.
